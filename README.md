# Lotus — a blooming

A photoreal, real-time **sacred lotus (*Nelumbo nucifera*)** that rises out of a misty dawn pond as a bud and unfurls, petal by petal, into a fully open flower — rendered with [three.js](https://threejs.org) (WebGL2) and **zero external assets**: every petal, leaf, texture, sky and ripple is generated by code.

It is built to look like macro film of a real flower, and to run well on phones.

## Run it

```bash
npm install
npm run dev            # http://localhost:5173  (also served on your LAN)
```

- **On a phone:** with the phone on the same Wi-Fi, open the *Network* URL that `npm run dev` prints (e.g. `http://192.168.x.x:5173`). If it doesn't load, allow Node.js through the Windows firewall for private networks.
- **Production build:** `npm run build` → static site in `dist/` (`npm run preview` serves it).
- **One double-clickable file:** `npm run build:single` → `dist-single/index.html` (≈970 KB with the birthday fonts, everything inlined, works from `file://`).
- **Live on GitHub Pages:** every push to `main` deploys — see [Deploy to GitHub Pages](#deploy-to-github-pages). Checks before you push: `npm run check` (unit checks, then a build).

> Don't open the source `index.html` — or the pages in `dist/` — by double-click: browsers block ES modules from `file://`, and the page will say "Still loading…". Use the dev server, `npm run preview`, a web host, or the single-file build.

## Pages (slash routes)

One app, several pages. The route only decides what is layered on top of the same pond:

| URL | What you get |
|---|---|
| `/` and `/home` | the plain blooming lotus (title card + controls) |
| `/nivashini` | the same bloom as a **birthday card**: a whisper (*A lotus for Nivashini*) as the stalk rises, then *HAPPY BIRTHDAY* appears letter by letter as the petals open, the name is written in gold script, and a short wish fades in while golden pollen-light lifts off the flower. The camera lowers the picture slightly (a lens shift) to leave sky for the lettering. |

- **Dev:** `http://localhost:5173/nivashini` (on a phone: the *Network* URL + `/nivashini`). Any path works with the dev server; unknown paths show the home page.
- **Build:** `npm run build` writes a real file per route — `dist/index.html`, `dist/home/index.html`, `dist/nivashini/index.html` — so it works on any static host (Netlify, GitHub Pages, S3, nginx …) with **no rewrite rules**; `/nivashini` simply redirects to `/nivashini/` like every static host does. `npm run preview` does the same (it also matches the URL case-insensitively, which a real Linux host will not).
- **Double-click:** `npm run build:single` writes `dist-single/index.html` (home) **and** `dist-single/nivashini.html` — the same self-contained file with that page's title. Each file is pinned to its page by a meta tag, so renaming one does not change what it shows; `index.html?route=nivashini` switches a copy.
- **The camera icon on `/nivashini` saves the finished card** (render + lettering) as `happy-birthday-nivashini.png`, up to 4K. Saved mid-reveal, it shows exactly the half-written screen; the picture is measured the instant the button is pressed, so a rotation while it renders cannot move the text.
- **Change the words / add a person:** edit `src/app/routes.js` — each page has a `greeting` (`whisper`, `headline`, `name`, `wish`). Copy the `nivashini` entry in `PAGES`, change its **key** (it is the page id and the URL: lowercase letters, digits, dashes) and the words, and `npm run build` emits the new page; the build refuses a table with a bad key or missing text. Long and two-word names, and long wishes, shrink to fit the screen. Timing of each line is `REVEAL` at the top of `src/ui/greeting.js`.
- Screen readers get the whole greeting (heading, dedication and wish) as ordinary text; with *reduce motion* on, the lettering cross-fades instead of writing itself, the framing starts in its final position and the sparkles drift at a third of the speed.

## Deploy to GitHub Pages

The repository publishes itself. `.github/workflows/deploy.yml` runs on every push to `main`: the Node-only unit checks, `npm run build`, then the official Pages actions.

1. **One time:** *Settings → Pages → Build and deployment → Source: **GitHub Actions***.
2. Push to `main`. The run (Actions tab) ends with the site URL.

It is a project page, so the pages live under the repository name:

| URL | What you get |
|---|---|
| `https://navi-04.github.io/lotus/` | the plain bloom |
| `https://navi-04.github.io/lotus/home/` | the plain bloom |
| `https://navi-04.github.io/lotus/nivashini/` | the birthday card (`/nivashini` without the slash redirects) |

Everything is relative (`base: './'`), so the same build also works under any sub-path or a custom domain. On GitHub Actions the build also writes `404.html` with a `<base>` pointing at the site root, so a mistyped link shows the lotus instead of GitHub's error page; set `PAGES_BASE=/` for a custom domain at the root. To test the live site: `npm run test:routes -- --base https://navi-04.github.io/lotus --static`.

## What you're looking at

| Part | How it's made |
|---|---|
| **Petals** (22, 4 whorls) | One merged mesh. The CPU integrates each petal's inextensible centre line from a bending-angle law every frame into two tiny float textures; the GPU builds the cupped cross-section, twist, margin ruffle and normals. Staggered per-petal schedules make the unfurl cascade from outer to inner whorls — tips loosen first, bases swing out later. |
| **Petal skin** | Thin-translucent-sheet shading inside three's light loop: wrap diffuse + back-lit diffuse transmission + forward-scatter lobe (petals *glow* where the sun shines through), light from the far side from the sky, satin sheen, dense anastomosing veins (colour + bump), pale-green-cream → blush → rose gradient, different inner/outer faces. |
| **Pod** | Obconical receptacle with 19 real carpel recesses, seeds and stigmas, basal collar, and sepals that clasp the bud and fall away as it opens. It grows as the flower matures. |
| **Stamens** | 110–340 GPU-instanced filaments with grooved golden anthers and club tips, bending with bloom and wind. |
| **Stalk** | Rebuilt each frame along a calibrated S-curve; rises from beneath the water (spawning ripples), bud nods then straightens, cantilever sway, instanced prickles. |
| **Leaves** | Floating pads that rest on the water and emergent funnel leaves; margins, tilt and flutter in the vertex stage; glaucous waxy bloom, radial veins that fork twice, back-lit lamina, lotus-effect water beads. |
| **Water** | Mirrored-camera planar reflection (half-float HDR), Fresnel, scrolling wave normals, expanding ripple rings, ambient raindrops, sun glitter, noise-driven ground mist, darkening under pads. |
| **Sky & light** | HDR dawn sky with sun halo and cirrus; the same sky is baked to an image-based light; shadow-casting sun with a texel-snapped frustum that follows the flower; haze, distant tree line, bokeh discs, sunlit pollen motes. |
| **Post** | Half-float HDR + MSAA, bloom, depth of field focused on the flower, Khronos *Neutral* tone mapping, split-tone grade, film grain + dither. |

## Quality tiers & performance

**Everything is maximum by default: every page starts on Ultra, on every device** (override with the Quality menu or `?quality=`; *Auto* in the menu = match the device instead). Because Ultra is the default, safety nets keep weak hardware smooth without anyone touching a setting:

- **The frame governor** (`src/render/adaptive.js`, simulated in `tools/adaptive-sim.mjs`). Smooth means frames that arrive at an *even* rhythm, so it works with two dials. **Pace**: how many display refreshes each frame lasts. It learns the display's refresh rate (the page measures it before any heavy work starts, `index.html`), never renders much above 60 fps (a 120 Hz phone draws every second refresh: the same look for half the work and heat), and when 60 cannot be held it moves to an even 30 instead of wobbling between 30 and 50. **Pixel ratio**: moved in whole steps of a short ladder (0.6 … 3×), because every resize re-allocates the render targets. A window (0.7 s) is *slow* when more than a quarter of its frames miss the deadline by 30 %; two slow windows in a row drop the ratio in proportion to the overload (warm-up and a capped mean keep start-up work and one-off hitches from costing anything). Resolution goes down only to a still-sharp 1.0× before the slower pace is taken, and the pixels are given back as soon as the deadline doubles. A descent that bought nothing (a CPU-bound stall, a battery-saver cap) is undone. Recovery is by probing — one step up in resolution after 20 s of calm (doubling to 8 min after a failed probe), one pace faster after 90 s (doubling to 24 min) — and a failed probe is reverted exactly. A saved picture never counts. `?pace=0` turns pacing off (benchmarks), `?dpr=` pins the ratio and turns the governor off. Measure it with `npm run smooth` (below): under the same heavy load it is a steady 30 fps with **0 late frames of 1,020** at a sharp 1.0×, where the old resolution-only control gave a wobbling 47 fps with **388 late frames of 1,637** at a blurry 0.75×.
- **Easing the effects** (`src/core/shed.js`, unit-tested). When the slowest pace at the sharpest worthwhile ratio is *still* late, the device is too weak for the scene as drawn, and the app gives up what nobody can point at, before it would go blurrier: the depth-of-field blur is computed at half resolution, and the shadows and the water reflection are refreshed every second (then third) frame, the reflection also drawn smaller. Each level is 15–30 % cheaper; nothing is switched off. The level is remembered for a week so a weak phone is smooth from the first second of the next visit; `?shed=0|1|2` pins it.
- **Phone profile.** Ultra on a phone keeps every effect (shadows, reflection, depth of field, bloom) but sizes the costs that do *not* shrink with the pixel ratio for a small screen: geometry density 0.85 (the seed pod alone is 142k triangles at 1.4), a 1024 shadow map, a 0.4× reflection; the pixel ratio starts at 1.5×. On the laptop test bench a phone-sized Ultra went from ≈ 42 fps with 11 hitches over 50 ms and a wandering resolution to a steady 60 fps with none.
- **Software renderers** (no real GPU: SwiftShader, llvmpipe …) start on Low — the *default* only: a tier chosen in the menu or in `?quality=` is honoured.
- **Crash guard** (`src/core/crashGuard.js`, unit-tested). Every boot holds a Web Lock until its first frames are out, so a later boot can tell a tab that died (killed for memory, driver reset) from another window that is still loading. A dead boot, or a lost-and-restored GPU context while the tab was visible, steps the *next* load down one tier (up to three) and says so; the step-down expires after a week, and reloading after context loss is limited to twice a minute. Picking a tier in the menu clears it; an explicit `?quality=` always wins. With blocked storage a menu pick travels in the URL.

| Tier | What changes | Measured on an Intel Iris Xe laptop GPU, 720p, DPR 1 |
|---|---|---|
| Low | no planar reflection, no shadows, SMAA, fewer instances | ≈ 135 fps |
| Medium | 0.3× reflection, 1k shadows, SMAA | ≈ 100 fps |
| High | MSAA 2×, 2k shadows, 0.5× reflection, depth of field | ≈ 50 fps |
| **Ultra** (default) | 4k shadows, 0.75× reflection, MSAA 4×, denser meshes, up to DPR 3 | ≈ 33 fps (≈ 31 fps on `/nivashini`, which adds sparkles + lettering) |

On phones MSAA is replaced by SMAA (multisampled half-float targets are unreliable on mobile GPUs), and the petal mesh is lighter (58 × 26 instead of 95 × 42). Single features can be overridden from the URL to measure what each costs: `?shadow=1024` `?refl=0.5` `?lod=0.85` `?dof=0`.

### The petals prove they draw (petal ladder)

The petals are the one part of the flower that needs more than stock drawing: each petal's surface is built in the vertex shader from per-row data. Phone GPUs differ in what they accept, and a draw they refuse is silent — the flower shows its stem, seed pod and stamens and no petals. So the app checks (`src/lotus/petalProbe.js`, `petalLadder.js`, unit-tested): before the loader lifts it draws *only* the petals, from the side, into a 64 × 64 hidden image and counts the pixels. If almost nothing is there it moves one rung down and tries again:

| Rung | How the same flower is drawn |
|---|---|
| `tex` (desktops) | row data in two float textures, read with `texelFetch` in the vertex shader |
| `inst` | the same data as instanced vertex attributes (no vertex texture, no uniform-array indexing) |
| `instlite` | instanced + a lighter skin (no noise, veins or screen-space derivatives) |
| `cpu` | the surface built in JavaScript, drawn with a stock `MeshStandardMaterial` — needs nothing special |

The probe draws the petals alone, so a second check watches the real frame (`src/lotus/petalWatch.js`): an occlusion query around the petal draw of the main camera asks the GPU whether any pixel of them got through. Once the flower is above the water and in view, 90 frames without a single pixel mean they are not showing whatever the probe said, and the app moves one rung down, live. The first pixel that passes ends the watch for good.

The rung that worked is remembered for a week (`lotus.petals`) so a device that needed a lower one does not pay for the failed ones on every visit; merely working does not renew the note. `?petals=tex|inst|instlite|cpu` pins a rung (it is measured and reported, never swapped) — handy for finding out which one a phone can do. On a healthy device none of this is visible: one probe, nothing stored, and the pixels are identical to the plain path.

**`?debug=1`** overlays the GPU name, its limits (varying / uniform vectors, vertex texture units, attributes), the petal rung with the probe's pixel counts for every rung tried, the live-frame verdict (`seen` / `watching n/90` / `blind`), and any shader that failed to build — a screenshot of it from a phone says what that GPU refused.

Reproduce with `npm run perf -- --url "http://localhost:5173/?quality=high&still=1&bloom=1&dpr=1" --uncapped`.

## URL parameters

`?quality=low|medium|high|ultra|auto` · `?route=home|nivashini` (pick the page when the path can't, e.g. `file://`) · `?bloom=0..1` (freeze the bloom stage) · `?rise=0..1` · `?t=seconds` · `?still=1` (fully deterministic frame) · `?cam=default|close|top|side|low|wide|portrait|x,y,z,tx,ty,tz[,fov]` · `?cine=1` (use the cinematic camera on a frozen frame) · `?dpr=1.5` (pins the pixel ratio and turns adaptation off) · `?hide=leaves,water,stamens,petals,pod,stem,env,post,sparkles,greeting` · `?tm=neutral|agx|aces` · `?glow=0.3` · `?exposure=1` · `?seed=123` · `?petals=tex|inst|instlite|cpu` (pin how the petals are drawn, see above) · `?pace=0` (no frame pacing) · `?shed=0|1|2` (pin the eased-effects level) · `?shadow=` `?refl=` `?lod=` `?dof=0|1` (override one feature of the tier) · `?debug=1` (stats, display refresh and pace, GPU limits, petal-probe overlay). Test hooks: `?breakpetals=tex,inst` pretends those rungs fail the startup probe, `?breaklive=tex` pretends they pass it but never show in the live frame (to exercise the ladder and the watch).

## Browser support

Needs WebGL2 (all current Chrome, Edge, Firefox and Safari 15+, iOS 15+). Honors `prefers-reduced-motion`, pauses when the tab is hidden, recovers from WebGL context loss, and respects phone safe areas.

## Troubleshooting

- *Choppy on a phone:* Ultra is the default, and the resolution already scales itself down under load; for more headroom open the Quality menu and pick **Medium** / **Low** (or **Auto** to match the device).
- *"Quality was lowered after a problem on this device":* the crash guard stepped down a tier after a lost GPU context / a tab killed while loading. **Quality › Ultra** restores it (it also expires by itself after a week). *"No graphics card found, so this runs on Low":* a software renderer; **Quality › Ultra** overrides it.
- *The petals are missing (stem, pod and stamens only):* the GPU refused the petal draw and the automatic check could not find a way around it. Open the page with `?debug=1`, screenshot the overlay, and try `?petals=inst`, `?petals=instlite` and `?petals=cpu` in turn — whichever shows petals can be made the default for that device.
- *"Still loading…" for more than 20 seconds:* the page cannot start. Opened from disk (`file://`) the module script is blocked — serve it (`npm run dev` / `npm run preview` / a web host) or use `dist-single/`.
- *Black screen / "couldn't start":* the device lacks WebGL2 — try `?quality=low`, a newer browser, or enable hardware acceleration.
- *The page loads but looks flat:* make sure it isn't running with `?hide=post`.
